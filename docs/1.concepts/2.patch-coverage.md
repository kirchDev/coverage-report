# Patch coverage

Patch coverage answers one question: of the lines this pull request added or changed, how many did the suite execute. It is the number the whole project exists for, and the one the surveyed alternatives approximate with a different question — coverage of the _files_ that changed.

The difference is not academic. A one-line fix in a four-hundred-line file is one line of patch. Reporting that file's other uncovered lines against the change is how a reviewer learns that the comment is noise, and a comment nobody reads gates nothing.

## How it works

A unified diff is reduced to a map of path to the set of line numbers the change added, in the file **as it now stands**. Four rules decide it, and each one is the difference between a true number and a plausible one:

- **Only the new side counts.** A removed line no longer exists and cannot be covered. A context line was not touched by this change and belongs to whoever wrote it.
- **A deleted file contributes nothing.** Its lines are gone.
- **A rename is followed under its new name**, because that is the name the coverage report will use.
- **The hunk header's start line is authoritative**, and the counter walks from it. `@@ -1 +1 @@` with the count omitted means a count of one, and `\ No newline at end of file` is a marker rather than a line, so it never advances the counter.

That map is then intersected with the report: a line is counted only when it is both in the diff and in the coverage data. `covered` is the intersection's hits, `total` is its size.

Two sources feed the same reader. On a pull request the Action takes the `patch` field of GitHub's files endpoint — hunks without the file headers around them — while the CLI takes a whole unified diff from `--diff`. Both go through one parser, because two diff readers is exactly how a comment and a check run start disagreeing.

## Why it's built this way

**A changed line the report says nothing about is not counted either way.** Blank lines, comments, imports, a closing brace: no coverage tool emits a record for them. Counting them as uncovered would make every formatting commit look like a regression; counting them as covered would inflate the number. Leaving them out is the only reading that stays honest, and it is why a documentation-only pull request reports no patch coverage rather than 0%, and never fails a `min-patch` threshold.

**A file with no coverage data at all drops out entirely.** A change to a workflow, a lockfile or a README has nothing to measure, and inventing a measurement for it would make the number meaningless where it matters.

**Files are listed worst-first.** The reason to open the section is to find what needs a test, not to read an alphabetical list of the files that are already fine.

The rules above are pinned by fixture tests in [`test/diff.test.js`](../../test/diff.test.js) rather than by judgement — the failure mode of this code is a number that is quietly off by a line, which no amount of reading catches. Change it against the tests.
